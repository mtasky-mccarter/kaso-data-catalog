# KASO Data Catalog — Generated Publication Standard

This document defines the repository layout and naming contract for generated human-readable KASO Data Catalog publications. Generated DOCX/PDF/viewer outputs remain derived publications; canonical machine-readable contracts on `main` remain the source of truth.

## 1. Publication directory

Every generated document family must have its own stable folder directly under `generated/`:

```text
generated/<publication-slug>/
```

`<publication-slug>` is version-independent, ASCII, lowercase and kebab-case. Examples:

- `generated/cestovne-prikazy/`
- `generated/vydajky/`

Do not place generated DOCX, PDF or publication manifest files directly in the root `generated/` directory.

## 2. Canonical filename

The required basename for Technical & Diagnostic Reference publications is:

```text
KASO Data Catalog - Technical & Diagnostic Reference - <subject_sk> v<documentation_version>
```

Rules:

- Keep the prefix exactly `KASO Data Catalog - Technical & Diagnostic Reference - `.
- `<subject_sk>` is the approved Slovak document subject and preserves Slovak diacritics and normal human-readable spacing.
- Use lowercase subject wording unless the approved document title requires otherwise.
- `<documentation_version>` is the current approved documentation/contract version from the canonical domain revision history. It must not be invented independently by a generator.
- Use the same basename for DOCX, PDF and publication manifest.

Example for cestovné príkazy v1.1:

```text
generated/cestovne-prikazy/
  KASO Data Catalog - Technical & Diagnostic Reference - cestovné príkazy v1.1.docx
  KASO Data Catalog - Technical & Diagnostic Reference - cestovné príkazy v1.1.pdf
  KASO Data Catalog - Technical & Diagnostic Reference - cestovné príkazy v1.1.manifest.yaml
```

Example for výdajky v1.1:

```text
generated/vydajky/
  KASO Data Catalog - Technical & Diagnostic Reference - výdajky v1.1.docx
  KASO Data Catalog - Technical & Diagnostic Reference - výdajky v1.1.pdf
  KASO Data Catalog - Technical & Diagnostic Reference - výdajky v1.1.manifest.yaml
```

## 3. Version rule

Publication versioning follows the domain documentation version. The generator/orchestrator must read the current `contract_version` from the canonical domain revision history and use it in the publication basename and manifest. A version change in canonical documentation therefore changes the generated filename automatically.

Do not use an unversioned publication filename. Do not silently overwrite a differently versioned publication by removing the version suffix.

## 4. Manifest rule

The publication manifest is colocated with the DOCX/PDF and uses the same basename plus `.manifest.yaml`.

Manifest artifact paths must point to the exact repository-relative canonical generated paths, including the publication folder and human-readable filename. Artifact SHA-256 values must correspond to the generated bytes.

## 5. Generation entrypoint

Canonical repository publication generation uses:

```text
python tools/generate_publication.py <publication-slug>
```

Use `all` to generate every registered publication family and `--check` to verify deterministic current output without replacing committed files.

Domain-specific generator scripts are implementation details. They may emit temporary intermediate filenames, but committed canonical publications must pass through the publication orchestrator and comply with this standard.

## 6. Validation

Repository tests must reject:

- DOCX/PDF/publication manifests stored directly under `generated/`;
- non-kebab-case publication folder slugs;
- generated document filenames that do not use the required prefix;
- missing or malformed `v<major>.<minor>` version suffixes;
- manifest artifact paths that do not resolve to the colocated canonical files;
- generated outputs that differ from deterministic regeneration.

A PR changing publication layout, naming or generator behavior must keep generic tests, domain publication tests and GitHub Actions green.

## 7. Scope and authority

This naming/layout standard controls generated publication artifacts only. It does not change Oracle semantics, domain contract IDs, canonical aliases, evidence requirements or documentation maturity. A filename or folder rename is a publication/repository change, not a business-semantic change, unless accompanied by a separate approved contract revision.
